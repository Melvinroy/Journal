# Modular Trading candidate: contracts and feasibility

Source review: 24 September 2026, baseline `b7fd102d3c614c449fef15f5c143bdeb8d9b285c`. This document defines the **target** boundaries for packages A–H of the [modular product plan](../trading-modular-product-plan.md). It is not evidence that the standalone candidate or any newly described endpoint already works. The [M01–M16 inventory](IBKR_PAPER_ACCEPTANCE_QC.md#modular-trading-baseline-inventory--24-september-2026) records the actual visible controls and current paper support.

## Product and module contract

Keep one local service and one built-in browser shell. Trading and Journal are **two selectable views over one Trading module and one ledger**. A module preference controls navigation and loading; it never grants broker access or interrupts background accounting.

| Owner | Contract | Failure behaviour |
| --- | --- | --- |
| Shell | Owns local profile/session, selected account/environment, navigation, view preferences, connection banner, version and recovery entry points. Built-in manifest has stable module ID/version, view IDs, required services and activation/deactivation hooks. | Missing/unavailable Trading service shows a locked, actionable state; do not fall back to sample data as executable data. |
| Trading module | Reuses `TradePlanner`, `TradingWorkspace`, `PaperOrderReview`, `PaperCampaignActions` and Journal presentation. Owns drafts, reviews and position UI; consumes the shell's verified identity, binding, status and server capabilities. | A hidden Journal view still records events. Trading cannot be disabled while owned exposure, working orders, uncertain commands or managed rules need attention. |
| Shared domain/service | Owns immutable plan revisions, command identity, broker adapter, durable events and one Position/Journal projection. Pure market-reference calculations may run headlessly without Charts/Scanners UI or EOD backfill startup. | Missing market references are unavailable; a chart/sample import is never an execution source. |

The standalone build must demonstrate that opening Trading/Journal imports no unrelated module UI and sends no scanner, chart or cloud-report requests. The existing all-workspace mode retains its behaviour until separately migrated. These are internal interfaces; no third-party plugin ABI or arbitrary module loading is offered.

The 25 September candidate source adds `modules.json` as a separate, versioned profile preference. It leaves the installed `profile.json` v1 format readable by an older candidate. The local-session GET/PUT `/v1/local/modules` routes report or atomically save the visible Trading/Journal views; both are selected when no sidecar exists. A remembered paper account prevents hiding Trading because current exposure is still unknown. Account confirmation uses the same profile lock and rejects a hidden Trading view. The Home/Connect source offers this choice and filters desktop/mobile navigation, but the latest source has not passed full TypeScript, browser or packaged verification. A hidden Journal view remains a presentation choice; durable event recording is not disabled.

## Identity and local service contract

Current baseline: `app/usePaperExecution.ts` sends a Supabase bearer token; `paper_auth.py` verifies the user against Supabase and an explicit owner/account binding. The standalone mode requires a **separate server-selected local principal**, not a browser-supplied switch that weakens the existing cloud mode. Cloud mode keeps its current authentication and ownership checks. No Supabase project, cloud login, telemetry or network call may be required at standalone startup.

| Interface | Required fields and invariant | Rejection/invalidation |
| --- | --- | --- |
| Local profile | Random installation/profile ID, owning Windows user identity and versioned preferences. Keep separate from legacy cloud UUID and IBKR account ID. | Wrong Windows user, unreadable owner state or missing private storage fails locked; never auto-adopt a nearby legacy database. |
| Launcher bootstrap | Random, short-lived, single-use capability issued by the local service to its own launcher. Exchange for a browser session; never persist it in a URL query, log or browser storage. | Expired/replayed or unrelated-process handoff rejected. An occupied port is not proof of Brontide ownership. |
| Browser session | HttpOnly same-origin cookie, CSRF protection for mutations, exact loopback Host/Origin checks and session generation. | Lock/logout, profile change and account/environment change revoke pending order/action reviews. Browser closure alone does not terminate healthy broker-held protection or the service. |
| Command authority | Server derives principal, account binding, environment, current policy and permissions; request contains command identity and relevant saved revision/digest. | Stale binding, absent fresh evidence, policy lock, unknown prior transmission or conflicting session blocks an economic command. No automatic retry of uncertain transmission. |

Bind the service to literal loopback only. Validate browser cookie/CSRF/Origin behaviour on the selected browser and loopback host. An operational pause is a separate command: it stops new entries and managed rules while retaining broker-held orders. Local same-user malware and administrators are outside the promised isolation boundary.

## Broker connection and capability contract

The Connect view must show separate facts: local service ready; official SDK present/compatible; TWS reachable; API usable; account discovered; environment corroborated; data fresh; reconciliation complete; execution permitted; managed rules active. Do not compress them into one “Connected” flag. `paper_service.py` currently exposes server-owned capabilities and separate locked/readiness states; retain that ownership.

The 25 September source adds a session-protected, read-only `/v1/local/sdk/metadata` inventory of `ibapi` package metadata in the standalone service's own Python runtime. It reports sanitized claimed version and exact protobuf pin, or fixed missing/unavailable labels. It deliberately reports official provenance unverified, dependency compatibility unknown and execution disabled in every case. Connect has an explicit request button in later source, but its changed screen has not passed exact-source browser verification. This is not an SDK installation step, a TWS probe or proof about another operator Python environment; the installed sample predates it.

The later metadata diagnostic now flags an exact declared `protobuf==5.29.5` pin with [GHSA-7gcm-g887-7qv7](https://github.com/advisories/GHSA-7gcm-g887-7qv7), which lists versions below 5.29.6 as affected. A different or absent pin remains **unverified**, never declared secure or compatible. The frontend parser rejects a missing, inconsistent or execution-enabled diagnostic, and the draft Connect card explains the known hold without enabling broker access. Focused backend and parser checks pass; the changed Connect presentation still requires an exact-source browser and installer check.

1. Probe only allowed local TWS endpoints after an intentional Connect action or a saved reconnect preference. Use bounded attempts, no LAN scan and no login/2FA automation.
2. Discover all reported accounts, then require explicit account/environment confirmation even when only one appears. Port number or label alone is insufficient evidence of paper/live identity. The first candidate supports one selected account at a time.
3. Persist a scoped binding only after confirmation. On a changed account, environment, SDK, connection generation, freshness or source revision, invalidate reviews and require full broker snapshot/execution reconciliation before any new entry or managed-rule resume.
4. Keep the existing approved command route and server policy. A new adapter must not expose an alternate submit path, raise the three-share paper limit, resume the halted 200-target session or bypass the submission-policy rejection.
5. TWS absent, API read-only, SDK missing/incompatible, stale market data, client-ID collision and ambiguous accounts must display a specific block and leave saved history available with age/unknown values.

The later source also has `LocalBindingStore`, a private first-binding contract without a production broker caller. Its `BrokerAccountObservation` must come from a future server-side adapter, never a browser body or the synthetic Connect fixture. Confirmation requires fresh paper identity, compatible SDK/API claims, a candidate in the observed list, the user's exact typed account and an independently saved owner reference for that exact ID. Binding schema 2 stores the reference's salted digest beside the profile ID, masked account, source/account digests and timestamp; it always says reconciliation required and execution disabled. A different account/source/reference cannot silently replace it. Schema-1 bindings lacking that exact reference link are preserved but unavailable, not upgraded from a matching mask. An operator-reviewed migration procedure is still required if such a real binding exists. This is isolated fixture evidence, not actual broker discovery, environment verification, Windows ACL proof or a completed account switch workflow.

The local service now also has an authenticated, read-only `/v1/local/binding` view. It shows a saved masked choice only when its private schema-2 reference link still matches; a missing, different or unlinked reference yields unavailable, including when two full account IDs have the same visible mask. It always reports current connection unverified, reconciliation required and execution disabled. A guarded account-selection route exists in later source, but the installed launcher supplies no broker evidence adapter, so its discovery and confirmation return unavailable and cannot create a real binding. IBKR documents `reqManagedAccts` as a list of accounts accessible to the TWS login, not as proof that the session is paper: [managed-account request](https://www.interactivebrokers.com/docs/tws-api/doc/account-portfolio-data/managed-accounts/request-managed-accounts). Its published paper port is a default, not authoritative identity: [market-data quick start](https://www.interactivebrokers.com/docs/tws-api/doc/quick-start/requesting-market-data). Do not set `paper_identity_verified` from the account prefix, port or browser selection alone.

**Paper-mode evidence gap:** IBKR says the [TWS API makes no distinction between live and paper logins](https://interactivebrokers.github.io/tws-api/third_party.html), and its [default live/paper ports can be changed](https://interactivebrokers.github.io/tws-api/initial_setup.html). Therefore a successful socket connection, `reqManagedAccts`, a `DU`-looking account, or port 7497 is not sufficient to assert paper mode. `LocalPaperReferenceStore` holds one owner-attested paper-account reference under the private profile, as a salted digest and masked label, without storing the raw account ID. It cannot silently switch accounts; missing, changed-profile, malformed and stale observations fail closed. The later source adds a local-session/CSRF-protected Connect form and `/v1/local/paper-reference` status/save route: the owner must type the same independently checked paper-account ID twice and affirm the IBKR paper-login check. Responses show only the mask and explicitly report paper identity unverified and execution disabled. Focused route/parser tests pass; the authored browser flows, rebuilt app and real owner account remain unverified. The local account-selection path still requires an exact match to that reference *in addition to* a server-owned paper/SDK/API observation and a separate typed account confirmation. The installed launcher supplies no corroborating broker evidence provider. A returning connection may refresh read-only data automatically but must not infer submission authority from a saved label. The reference alone never proves actual paper mode, reconciles positions or unlocks orders.

`matched_account_for_reconciliation` can later identify the one remembered account in a fresh, verified multi-account observation without storing the full account ID. It refuses missing, changed-source, stale and uncorroborated observations. The returned account is for subsequent broker snapshot/execution reconciliation only; the method does not approve a review, arm a campaign or enable trading.

**Ledger-binding integration gate:** The remembered local `accountBinding` and the existing paper campaign `accountBinding` are different hashes. `LocalBindingStore` hashes the exact account, paper environment and discovery source; `PaperGatewayConfig.binding()` hashes account, host, port and client ID. A matching label, account prefix or either digest alone cannot establish that an existing campaign belongs to the local profile. A source-only `candidate_ledger_scope` now checks a fresh verified observation against the remembered exact account, the local discovery endpoint and a same-host/port paper gateway configuration. Its resulting scope accepts only new campaigns with the matching local profile ID, ledger digest and paper environment; legacy campaigns without those fields remain outside it. Isolated tests passed, but this bridge neither proves ledger ownership nor reads, imports, mounts or reconciles a real ledger. Before mounting a real Journal reader, the server must verify the private ledger and reject the whole history on a missing or mixed scope rather than silently returning an empty Journal. Keep the account number and mapping private; the browser receives only scoped, sanitized records. The installed sample has no real-history reader.

An unpackaged, source-only `LocalAccountSelection` ties an ephemeral masked choice to one authenticated local browser session and one fresh discovery generation. Saving a choice requires the exact typed account and a later server-side observation with the same account list/source/generation, newer timing, and verified paper/SDK/API evidence. Relaunch, lock, expiry, changed evidence, unavailable private profile or competing confirmation fails closed. The selection ID is not broker authority. The later standalone service mounts `/v1/local/account-selection` and its `/confirm` action behind local authentication, same-origin and CSRF checks. They accept no browser-supplied broker observation, sanitize provider errors, and recheck session authority after each server-owned read. Isolated route tests pass, but the installed launcher still supplies no paper-mode corroboration adapter or Connect caller; both actions are unavailable in the real candidate. The sample cannot save a real account or place an order.

`TwsManagedAccountReader` is a separate, source-only read adapter for candidate discovery. It requires a separately approved SDK flag, exact loopback address, bounded timeout and dedicated nonzero client ID. It waits for API readiness, calls only `reqManagedAccts`, rejects missing/conflicting/duplicate/invalid callbacks, disconnects, and waits a bounded time for its reader to stop before publishing masked choices. A late conflicting callback or reader that does not stop blocks the result. Paper identity remains **unverified** and execution disabled. Its old-paper-order transport is unchanged. It has no HTTP route or installed UI caller, and the repository runtime lacks the official SDK; isolated mocked callbacks are its only execution evidence. A later connected implementation must establish version/provenance and corroborate the actual TWS paper login before it may create `BrokerAccountObservation` with `paper_identity_verified=True`.

The later Connect source reads only `/v1/local/binding` under the existing local session and displays the masked remembered paper choice. It validates the response as disconnected, reconciliation-required and execution-disabled. It does not discover accounts, establish paper mode, reconnect TWS, authorize orders or expose the full account number. The normal Journal uses the same response parser to decide between clearly labelled sample data and protected recorded history. Focused parser tests pass; the new Connect browser regression is written but unrun against the current source.

The current server `CAPABILITIES` allows paper Long, Limit/capped midpoint/stop-limit breakout, Regular or RegularExtended, DAY only, excluding PL/AMD; RegularExtended additionally requires Limit + STP LMT. Shorts, GTC, overnight and four populated legs are visible/plannable gaps, **not executable standalone promises**. Actual paper order submission is globally locked. Full planner remains the eventual product target; each expansion needs separate semantics, deterministic checks and broker qualification.

## Ledger, storage and migration contract

The ledger is the source of truth for owned campaigns. Position and Journal views consume the same projection. An approved immutable plan revision and command intent are durable before transmission. Exact broker order/execution identities and event order determine ownership; duplicate or reordered callbacks must not duplicate a trade. Unknown transmission remains unknown until reconciliation, never automatically resent.

The later source adds a **read-only** `LocalRecordedJournalSource` for a separately provisioned private paper ledger. It requires an exact private marker tying the local profile, confirmed account digest, separate paper-ledger digest and environment together. Every recorded batch and campaign must carry the same local user, ledger digest and paper environment; any missing, legacy, synthetic or mixed-scope row rejects the entire history. Batch approval and campaign commands retain their unknown state. The recorded reader accepts the actual paper lifecycle's `cleanup` exit role separately from a synthetic manual exit. The response strips raw callbacks and account IDs, preserves unknown fees and exposure, and never claims current broker reconciliation. The standalone service mounts `/v1/local/journal/recorded` behind its normal local-session guard. The route requires the already-confirmed private binding and exact marker under that profile; missing or mismatched data returns unavailable. It rechecks session, saved account choice and ledger marker after reading, rejecting a lock or scope change before returning old records. Isolated API tests pass. The later browser source requests this route when a paper-account choice is remembered, validates the returned records, uses the shared Journal projection, and never combines recorded and sample rows. Missing or invalid history is shown as unavailable, not as zero records or zero exposure. Focused adapter tests pass, but the new browser regression cases, current-source TypeScript/build and direct browser verification remain open. No installed app creates the marker or verifies a real ledger. The synthetic fixture route remains test-only. The browser source preserves `cleanup` as a separate execution role and labels it “bounded closure” in Position and Journal; a focused pure projection test passes, but this rendered change has not passed current-source browser verification.

An internal `LocalRecordedStorePreparation` now creates a new empty `paper-recorded` ledger only under the existing profile lock, with submissions disabled, the private owner-attested paper reference matching the exact remembered account, and a fresh paper-account observation matching the remembered binding and gateway configuration. Missing or different references reject preparation; if the reference disappears later, existing ledger bytes remain intact but cannot be prepared again. It writes the strict owner marker last, refuses to adopt legacy or partial directories, and returns the existing read-only source only after validating it. An isolated full-path fixture then wrote two scoped artificial campaigns and read them through the authenticated `/v1/local/journal/recorded` route with Journal visible and hidden. A late fee changed only its campaign's result; the other campaign's unknown fee, unresolved command and unknown exposure were preserved, and a locked session was denied. This establishes preparation-to-read and view-independent history access in a fixture only. There is no installed caller, independently established paper identity, real broker event, or source-qualified package; it does not prove installed background recording or connect the ordinary Trading buttons to the ledger.

A separate-process durability fixture closed the writer, started another Python interpreter against the same isolated profile, rebuilt the local FastAPI service, required a new browser bootstrap and read the saved synthetic campaign through `/v1/local/journal/recorded`. The unauthenticated read was denied; the authenticated campaign remained visible while fee, unresolved command and current exposure stayed unknown. This proves persisted-read semantics across a fresh test service process; it is not an installed service restart, Windows reboot, TWS reconnect or broker accounting check.

In the later unqualified frontend source, entering either Plan & Position or Journal loads the same protected recorded-history response. The Position section uses the validated Journal rows for recorded entered/exited/remaining shares, fees and net result, marks them as last saved rather than current broker exposure, and keeps sample positions out of the confirmed-account view even if history is unavailable. Hiding Journal as a view does not stop the history read in Trading. A source-level browser regression now covers navigation and unavailable history, but it has not run against an exact-source preview. The installed candidate predates this change, and no live broker position, current stop or cleared-order claim follows from the saved rows.

**Private planner drafts, latest-source candidate:** The installed `d488631e` sample still uses profile-scoped browser drafts and has no confirmed paper binding or prepared ledger. Later unqualified source gives `TradePlanner` a separate account-backed mode after `WorkspaceApp` verifies the recorded-history and private-plan scope. In that mode ordinary **Save plan** and **Save exits** call `lib/local-private-plan.ts`; they never use the sample draft key. While account scope, history or the saved plan is being checked or is unavailable, the planner fields are hidden and neither save is offered; an unsaved in-memory edit can reappear only after the same scope is verified again. A completed private save displays its archived revision; editing leaves the prior revision intact, and an interrupted or uncertain write requires a read-only reopen before another save. Sample market snapshots are rejected even if a caller labels their captured price “Manual.” The simulated paper-intent control and broker order review do not appear in this mode. The sample mode retains its existing browser-only behavior.

The recorded-history response and private-plan status are separate reads. Both now carry the same server-derived opaque profile/account/ledger scope; `WorkspaceApp` publishes recorded history and enables private saving only when those values match. A mismatch clears the previous plan scope so an older account's draft cannot remain mounted as the current account's plan; a failed status leaves the account-backed view unavailable. The later frontend guard also hides old plan fields during a recheck or failed saved-plan read, while keeping the component's in-memory draft for a successful same-scope recheck. The save route independently checks the expected scope again before writing, since a browser comparison cannot authorize a save or guarantee an account will remain unchanged. Focused Node tests and syntax checks passed; the changed rendered path and ordinary-control browser cases remain unrun, so the latest source is not release-qualified.

`LocalSavedPlanStore` archives complete version-2 planner revisions as immutable, content-digested objects in a prepared profile/account/paper-scoped ledger. Session/CSRF-protected `POST /v1/local/plans`, `GET /v1/local/plans/{plan_id}`, `GET /v1/local/plans/current` and `GET /v1/local/plans/status` serve that exact scope. The opaque scope identifier isolates UI state but is not authentication. A save supplies its expected scope, per-plan revision and `expectedActiveRevision` (the account's last observed active plan revision, or `null` when no plan existed). The server compares both versions inside the ledger transaction for any new revision or plan identity; an identical already-saved revision may be acknowledged without another write. Stale saves cannot reactivate an old plan or silently replace a newer active plan. The last-saved pointer and revision are atomic; damaged content or an unidentifiable orphan plan head blocks new saves for inspection. These routes always report review and execution disabled and make no broker call. Focused backend/client tests pass. The new planner source has syntax checks and an unrun isolated browser regression. It still requires current-source TypeScript, browser, package and installed-account evidence before this integration can be called complete; the generated-file policy block remains in force.

The private plan boundary now rechecks that the remembered binding still matches its exact owner paper reference before returning scope status, reading a revision or writing a new revision. A missing reference or a syntactically valid replacement with the same visible mask leaves the archived plan intact but unavailable. Temporary-ledger tests exercise both the store and the normal session-protected plan routes. This closes a source-level isolation mismatch with recorded Journal; it does not establish current broker account identity or qualify the installed planner.

Private data are scoped by local principal, exact broker account binding and environment. Keep binaries and data in separate versioned locations under the owning Windows profile, with restricted ACLs and protected local secrets. Record snapshot capture/reconciliation times. On failed refresh, retain the last complete snapshot labelled stale; unknown exposure, fees and historical fills must not become zero. External TWS positions remain visible separately and are not silently assigned to a Brontide plan or controlled by owned-order actions.

Legacy import is an explicit, reversible operation: read a consistent source backup; verify owner/account/environment and schema; show dry-run counts, conflicts and unresolved commands; preserve original IDs, revisions, event ordering, fees and provenance; then import into a private target only when no second active service manages those broker identities. Never copy the owner's current records into build fixtures. A fresh install must not claim an existing folder by name. The earlier agent-versus-desktop private-folder discrepancy remains an operator gate, not resolved by a new candidate profile.

## Packaging and version contract

The current package experiment uses `scripts/package-windows-candidate.ps1` and PyInstaller 6.22.3 to produce a one-folder ZIP; `docs/trading/CANDIDATE_INSTALL.md` correctly labels it a **locked candidate/contributor path**, not a public one-command installer. It needs clean-machine installation, launcher, shortcut, update and rollback proof before changing that claim.

The eventual manifest records product and source version, Windows architecture, supported Python/SDK/TWS combination, frontend asset hashes, dependency inventory/license notices, schema version and verification evidence. A released installer and its one-command alternative must refer to the **same immutable artifact** and independent publisher provenance; a checksum next to an attacker-controlled binary is insufficient. Build/install never modify global Python, Node, PATH or another Brontide installation. Stage updates side by side, require an explicit update, consistent backup and schema compatibility check, and block update with owned exposure, working orders or uncertainty. Uninstall preserves financial data by default.

### Package A exit criteria

- Review M01–M16 against actual controls and source policy; retain the historical broker evidence separately.
