# Standalone Journal fixture reader

This is a development contract for the locked modular candidate, not an owner-data migration or broker acceptance result. `brontide_eod.local_journal.LocalJournalSource` reads the existing `PaperStore` campaign table and applies the existing `paper_domain.summarize` projection. It never connects to TWS, transmits a command, creates a database, discovers a nearby ledger or changes the installed owner store.

The reader has no default path. An isolated caller supplies an absolute fixture directory containing `ledger.sqlite3` and `synthetic-journal.json`. The marker identifies schema 1, `syntheticOnly: true`, an exact local profile ID, an independently selected `fixture-…` account binding and `paper` environment. Every campaign must carry the same scope and `syntheticOnly: true`. Wrong, unscoped or mixed campaigns fail the entire read. There is **no HTTP route** for this adapter; the packaged standalone service does not mount or call it.

The response contains recorded campaign counts, quantities, gross result, fees, net result and Execution R. Its `journalCampaigns` detail contains validated fixture plan/execution fields for a future Journal adapter, including the caller-supplied `fixture-` account binding and selected numeric order and contract IDs. Fixture creators must use synthetic IDs; the marker is a scope check, not proof of their origin. The response omits raw callbacks, private notes and private ledger paths. Missing fees remain unknown. `recordedOpenQuantity` describes recorded executions only; `currentExposure`, `ordersCleared` and `lastBrokerReconciledAt` remain `null`, and the connection is `not-connected`. A valid empty ledger returns `no-records`; a missing, malformed or unowned fixture is unavailable. The packaged Journal continues to show separately labelled sample trades; it does not consume this response.

Focused synthetic checks cover partial exits, late fees, corrected price, duplicate callback identity, a consistent SQLite backup, read-only reconstruction, persisted unknown command state, missing scope, timestamp validation, and sanitized Journal detail. There is no mounted route or session integration to verify yet. The existing frontend `paperJournalRow` mapper hard-codes IBKR provenance, so fixture detail must not be passed to it without an explicit synthetic identity/provenance adapter and a narrowed type contract. These checks do not prove an operating-system restart, broker reconnect, complete historical fills, protected open positions, user data migration or current account ownership. The separately gated future integration must bind a confirmed broker account to the local principal and reuse the same projection without treating this marker as broker evidence.
